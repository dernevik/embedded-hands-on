# Lab 4 — SPI Polling: Personal Learning Notes

## 1. What I learned about SPI

SPI is a synchronous, full-duplex communication interface. Unlike UART, there is no independent transmit or receive timing: the master generates the clock, and each clock cycle advances communication in both directions.

In the setup:

- **SCK** — clock generated by the master.
- **MOSI** — data from master to slave.
- **MISO** — data from slave to master.
- **CS/NSS** — identifies when the slave is selected.

We configured both STM32F446RE boards for **SPI mode 0 (CPOL = 0, CPHA = 0)**. SCK is idle LOW, data is sampled on rising clock edges, and the next bit is prepared on the opposite edge. The first bit must already be valid before the first rising edge.

Distinguish two parameters:

- `DataSize = SPI_DATASIZE_8BIT` determines the number of bits in one SPI data frame.
- `Size = 2` in `HAL_SPI_TransmitReceive()` specifies two data frames.

Transferring two bytes requires 16 SCK pulses.

With the master clocked from an 84 MHz APB2 peripheral clock and an SPI prescaler of 256, our SPI clock was:

`84 MHz / 256 = 328.125 kHz`

A two-byte transaction takes approximately 49 µs of clock activity.

### Full-duplex has an important consequence

There is no separate, clock-free "read" operation in SPI.

Even when the master only wants to receive data, it must generate SCK pulses. During those pulses, it also transmits bits on MOSI.

In our response transaction, the master sent `00 00` as dummy data in order to clock two response bytes out of the slave.

The dummy bytes did not have to be zero, but their interpretation must be defined by our application protocol.

## 2. About HAL, polling, and SPI hardware

`HAL_SPI_TransmitReceive()` uses peripheral status flags to move data between application buffers and SPI hardware.

Relevant flags include:

- **TXE** — the peripheral's transmit buffer is empty and can accept more data.
- **RXNE** — received data is available to read.
- **BSY** — the peripheral indicates ongoing SPI communication activity.
- **SPE** — the SPI peripheral is enabled.

These flags describe different aspects of the peripheral. In particular, `TXE = 1` does not mean that all transmitted bits have finished appearing on the wire.

### A debugger observation worth remembering

When the slave had entered a blocking two-byte `HAL_SPI_TransmitReceive()` call but the master had not yet generated any clock pulses, I observed:

```text
hspi1.TxXferCount = 1
hspi1.RxXferCount = 2
```

HAL has already handed the first transmit byte to the SPI peripheral. Therefore, its transmit counter had decreased.

No byte had yet been received, because no SCK pulses had arrived from the master.

This made the distinction between **software progress and hardware progress** very concrete.

### What blocking polling actually means

While waiting for the next SPI event, the CPU repeatedly executes HAL code and checks peripheral status flags.

The CPU is not manually sampling SCK or monitoring every clock edge. The SPI hardware handles the actual shifting and sampling.

The hardware also handles the slave's NSS input. HAL does not need to poll the CS GPIO directly during the transfer.

An indefinitely blocking call using `HAL_MAX_DELAY` can therefore leave the CPU waiting until the master provides the necessary clocks.

Another point:

```c
response_status = HAL_SPI_TransmitReceive(...);
```

The assignment to `response_status` happens **after the function returns**.

If the debugger stops while the CPU is still inside that function, `response_status` is still contain its initialized value, such as `HAL_ERROR`.

### General HAL code versus specialized drivers

HAL contains configuration checks, such as distinguishing 8-bit from 16-bit operation.

A specialized driver supporting only 8-bit SPI could omit the 16-bit implementation and potentially reduce overhead and code size.

However, the STM32F4 HAL already chooses its data-size-specific transfer path outside the main transfer loop. Removing the condition would not suddenly make SPI clocking faster.

For this lab, using HAL unchanged was the right choice. Comparing HAL, LL, and direct register access could be an interesting future optimization experiment.

## 3. SPI transactions versus application protocols

Our first experiment exchanged two bytes simultaneously:

| | MOSI | MISO |
|---|---|---|
| Transaction | `01 37` | `A5 5A` |

The slave's transmit buffer was prepared in advance. This demonstrated full-duplex communication, but it was not yet a dynamically calculated response to the command.

We then implemented two separate transactions:

| | MOSI | MISO |
|---|---|---|
| Request | `01 37` | `A5 5A` |
| Response | `00 00` | `81 37` |

Between the transactions, the slave interpreted the request and calculated:

```c
response_tx[0] = slave_rx[0] | 0x80U;
response_tx[1] = slave_rx[1];
```

`81 37` was derived from the received request rather than hardcoded.

### Why use two transactions

In our blocking HAL implementation, the CPU cannot execute the application-level response calculation while it remains inside the same blocking transfer call.

The SPI peripheral may already need the next transmit byte before the application has finished receiving and processing the previous one.

So, communicatio was split into:

1. Receive request.
2. Process request.
3. Transmit calculated response.

This was a protocol design choice, not an SPI limitation. Other SPI devices and protocols can exchange commands and responses within one CS assertion if timing support it.

### Synchronization matters

We used a short delay between request and response so that the slave could prepare its next transfer.

This works in our controlled experiment, but a fixed delay is not necessarily robust.

For a continuously operating system, I would consider either:

- **Master polling:** Periodically ask the slave whether its response is `BUSY`, `READY`, or `ERROR`.
- **READY GPIO:** Let the slave signal response availability using a separate GPIO, potentially connected to an interrupt input on the master.

Both approaches should include timeouts and error handling. A more complete protocol could also use transaction IDs, defined error codes, and data integrity checks.

I also learned that a slave must be prepared for repeated requests. Our initial single-transaction firmware was not automatically ready for another exchange once its blocking call had completed.

## 4. The difficult debugging episode: shifted SPI data

This was the most instructive part of Lab 4.

We initially achieved correct communication without the logic analyzer connected.

However, when using the SparkFun analyzer, we repeatedly observed corrupted data.

Expected:

```text
Master MOSI: 01 37
Slave MISO:  A5 5A
```

Observed in the problematic setup:

```text
Master MOSI: 01 37
Physical MISO: 4A B4
Slave RX:      80 9B
```

The pattern was interesting.

`A5 5A` becoming `4A B4` is consistent with the slave's transmitted bitstream having advanced by one bit.

Similarly, `01 37` becoming `80 9B` is consistent with an additional leading sampled bit on the slave's receive side.

**Our hypothesis was that the slave had interpreted an unintended SCK edge as a real clock edge.**

### The measurement setup affected the result

We performed an A/B/A-style experiment with the analyzer's USB connection:

- Analyzer USB connected: corrupted slave reception.
- Analyzer USB disconnected: correct slave reception.
- Analyzer USB reconnected: corrupted reception again.

This established a correlation between analyzer connection state and communication behavior.

The problem was not merely an incorrect PulseView decoder interpretation: corrupted data was also visible in the slave's RAM.

We did not establish the precise electrical cause.

### The successful firmware change

Our original master sequence selected the slave immediately before calling `HAL_SPI_TransmitReceive()`.

We changed it to:

```c
/* Enable SPI before selecting the slave */
__HAL_SPI_ENABLE(&hspi1);

/* Allow SCK to settle */
HAL_Delay(1);

/* Select slave */
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_6, GPIO_PIN_RESET);

spi_status = HAL_SPI_TransmitReceive(
    &hspi1,
    master_tx,
    master_rx,
    2,
    100
);

/* Deselect slave */
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_6, GPIO_PIN_SET);
```

With SPI enabled and SCK given time to settle before CS went LOW, communication became correct even with the analyzer connected.

This supported the hypothesis that the SPI activation/CS timing was relevant.

**Important qualification:** We changed both the SPI enable timing and introduced a 1 ms delay. We did not isolate which change was necessary. Nor did we capture the suspected unwanted clock edge directly.

What we verified was the successful corrective, not the exact physical root cause.

## 5. Logic analyzers

The SparkFun logic analyzer and PulseView provided direct visibility into the SPI signals.

I learned how to configure the SPI decoder, choose a trigger, and correlate captured data with the debugger.

Our relevant channel mapping was:

```text
D0 = CS
D1 = SCK
D2 = MOSI
D3 = MISO
```

### Sampling frequency is critical

At a 20 kHz sampling frequency, samples are taken every 50 µs.

Our SPI clock runs at approximately 328 kHz, corresponding to about 16.4 clock periods between samples at that sampling rate. Inadequate for decoding our transfer.

At 16 MHz, the sample interval is 62.5 ns, providing approximately 49 samples per SCK period.

### A logic analyzer is not an oscilloscope

A digital logic analyzer normally records whether a sampled voltage is above or below a logic threshold.

It does not reveal the complete analog waveform.

A very short glitch may fall between samples, even when the decoded waveform otherwise looks perfect.

We cannot conclude that SCK was free from narrow unwanted pulses because PulseView displayed clean clock edges at 16 MHz.

An oscilloscope would be useful for investigating:

- Short glitches
- Rise and fall times
- Ringing and overshoot
- Actual signal amplitudes
- Effects of probes, wiring, grounding, and loading

### Measurement can change system behavior

A probe is not electrically invisible. Its input characteristics, capacitance, ground connection, power state, and wiring can influence the circuit.

The right debugging approach is to vary conditions systematically and compare behavior both with and without the instrument.

In our case, observing corrupted data in MCU RAM was particularly useful because it showed that the issue went beyond the analyzer's display.

## 6. Practical lessons about the development setup

Several seemingly small details turned out to matter.

**Board identity:** With two identical NUCLEO-F446RE boards, assigning the correct ST-LINK serial number to each CubeIDE debug configuration prevents confusion about which MCU is being programmed and observed.

**Pin identification:** Physical header positions need to be checked carefully against board documentation. During setup, a miscount around the ST Morpho connector caused a grounding/pinout problem and temporarily prevented normal debugger connection.

**Power domains:** An unpowered MCU can potentially be partially powered through connected signal lines and input protection structures. We observed behavior consistent with back-powering when one board was disconnected from USB but SPI connections remained.

**Debugger timing:** Breakpoints during an active SPI transaction can distort or interrupt the experiment. A better sequence is to stop the master before CS assertion, prepare the slave and analyzer, then let the complete transaction execute without an intermediate breakpoint.

**Capture windows:** At 16 MHz, 100k samples cover only 6.25 ms. To capture both request and response, the total recording window must include the gap between them. I reduced the inter-transaction delay to fit both transactions into one PulseView capture.

**Preserving evidence:** Saving `.sr` captures alongside firmware allows revisiting the actual recorded SPI traffic rather than relying on screenshots or memory. We established `lab04-spi-polling/captures/` as our convention.

## 7. What I want to remember from this lab

My main takeaways are:

1. **Full-duplex is a hardware characteristic; request/response is an application protocol.** They operate at different conceptual levels.

2. **HAL state and physical bus state are different things.** A byte can have been handed to a peripheral without having been clocked out.

3. **CS, SPI enable, and SCK are distinct mechanisms.** Their timing and ordering can matter, even when the application code appears logically correct.

4. **A return status is not a complete proof of communication correctness.** `HAL_OK` does not replace checking actual payloads and protocol behavior.

5. **Instrumentation must be treated as part of the experiment.** Both measurement settings and electrical loading can affect conclusions.

6. **Reproducible experiments are more valuable than speculative fixes.** Predictions, debugger observations, physical captures, and controlled changes helped us understand an otherwise confusing failure.

7. **A working two-byte transfer is only the beginning of a communication system.** Repeated operation requires defined protocol states, synchronization, error handling, and recovery.

### Open question worth revisiting

We never directly measured the suspected unintended SCK edge or isolated the exact electrical role of the logic analyzer.

The early-SPI-enable sequence solved the problem in our setup, and the bit-shift patterns strongly supported the extra-clock hypothesis. But the exact mechanism remains unproven.

A future signal-integrity experiment using an oscilloscope could investigate this further.
